# Contract-First Architecture (API ↔ Frontend)

> Status as of 2026-06-23. How the shared contract drives the server, the docs, and the web client — and what's still needed to be contract-first *without caveats*.

## Summary

`packages/contract` is the single source of truth. Both the API and the web client are derived from it, so a schema change breaks compilation on **both** sides — and now also a frozen, CI-drift-checked `openapi.json` artifact. As of 2026-06-23 the four remaining gaps below are closed: this is now **spec-first** (the web client is generated from the committed OpenAPI document, not the server's types).

## The one source of truth — `packages/contract`

- `src/schemas.ts` — Zod schemas (`ObservationSchema`, `ProblemSchema`, `ProblemDetailSchema`, `GraphSchema`, `CreateObservationSchema`, `CreateProblemSchema`, `SynthesizeProblemSchema`, `CreateSolutionSchema` (polymorphic `targetKind`/`targetId`), `FeedItemSchema` (discriminated union on `kind`) + `ItemPageSchema` for the unified `/v1/items` feed, `ProjectTagsSchema`, …) with `.openapi()` metadata.
- `src/routes.ts` — `createRoute()` definitions (method, path, request, responses) for every endpoint, exported individually and as a `routes` map.

Nothing in this package depends on the server or the client. It is the contract.

## How each side is derived

```
                       packages/contract
                  (Zod schemas + createRoute defs)
                          │
          ┌───────────────┼─────────────────────┐
          ▼               ▼                     ▼
   apps/api (server)   /doc + /ui          apps/web (client)
   OpenAPIHono         Swagger UI          hc<AppType>
   • routes ARE the    generated from      • AppType built from the
     createRoute defs    the same routes      chained .openapi() routes
   • runtime Zod                            • paths/methods/params/body/
     request validation                       response types all inferred
   • response types
     compile-checked
```

### Server (`apps/api`) — full derivation
- The `createRoute` objects are fed directly to `OpenAPIHono` via `app.openapi(route, handler)` (`apps/api/src/index.ts`).
- **Runtime validation:** request params/query/json are validated by Zod from the contract; `c.req.valid(...)` returns typed, validated input.
- **Compile-time:** each handler's response is type-checked against the contract's declared response schemas/status codes.

### Docs — full derivation
- `/doc` serves the OpenAPI 3.0 document and `/ui` serves Swagger UI, both generated from the same route defs.

### Client (`apps/web`) — type derivation via `hc`
- `apps/web/src/api.ts` uses `hc<AppType>(...)` where `AppType` is exported from `apps/api`.
- **Critical detail:** the routes in `apps/api/src/index.ts` are **chained** (`app.openapi(a,h).openapi(b,h)…`) so the route types accumulate onto the returned app. Writing them as separate `app.openapi(...)` statements collapses `AppType` to `unknown` and breaks `hc` inference.
- Paths, HTTP methods, path/query params, and request bodies are all inferred and compile-checked. Responses are narrowed to the success shape via `res.ok` and pinned to the contract types.

**Guarantee:** rename a route or a field in `packages/contract` → both `apps/api` and `apps/web` fail to compile.

## Gaps closed (2026-06-23)

All four gaps that previously held this at "~85%" are now closed:

1. **Client decoupled from the server type.** `apps/web/src/api.ts` uses `openapi-fetch`'s `createClient<paths>` where `paths` is generated by `openapi-typescript` from the committed `openapi.json` (`bun --filter @cedarpad/web gen:api`). The `import { AppType } from "@cedarpad/api"` is gone — web depends only on the spec.
2. **Client-side response validation.** A small `unwrap()` in `api.ts` validates every success body against the matching `@cedarpad/contract` Zod schema, so a drifted server is caught at the boundary.
3. **Spec frozen + drift-checked.** `bun run openapi:emit` (`apps/api/scripts/emit-openapi.ts`) writes repo-root `openapi.json` from the contract-derived app; `apps/api/src/openapi.test.ts` regenerates and `toEqual`s the committed file (fails CI on drift) and asserts the security schemes.
4. **Auth modeled as security schemes.** `apps/api/src/index.ts` registers `ApiKeyAuth` (`x-api-key`) and `DevWorkspace` (`x-dev-workspace`) via `openAPIRegistry.registerComponent`; `packages/contract` attaches `security` to every `/v1/*` route, so the schemes appear in the doc, Swagger UI, and the frozen spec.

**Regen workflow:** after any `@cedarpad/contract` change, run `bun run openapi:emit` then `bun --filter @cedarpad/web gen:api` (the drift test guards against forgetting the first; web typecheck guards the second).

## Key files

- `packages/contract/src/schemas.ts`, `packages/contract/src/routes.ts` — the contract (schemas + routes, `security` per `/v1/*` route).
- `apps/api/src/index.ts` — `buildApp()`; chained `.openapi()` routes; `DOC_CONFIG`; security-scheme registration; `export type AppType` (kept; web no longer imports it).
- `apps/api/scripts/emit-openapi.ts` + `apps/api/src/openapi.test.ts` — emit + drift gate for `openapi.json`.
- `openapi.json` (repo root) — the committed, frozen spec; the web client and any polyglot consumer derive from it.
- `apps/web/src/api.ts` + `apps/web/src/api-types.ts` — `openapi-fetch` client over generated `paths`, with contract-Zod response validation.
