# v1.1 conversation tree: nested branches, no Turn Node, single fork verb

cedarpad v1 modeled conversations as a flat sibling list under a Thread Root: alternating user prompts (Content Nodes) and Turn Nodes, where each Turn Node parented Block Nodes (text / tool_use / tool_result). Branching created a new sibling Thread under the same Thread Root with cloned history. Three verbs (Branch, Retry from here, New thread sibling) covered different fork modes.

v1.1 reshapes this. The data and verb model are simpler; the rendering is closer to how a conversation actually reads in an outliner.

## What changes

- **Shape B**: each Prompt parents its own Block children. The `kind: 'turn'` node is removed entirely. A Prompt is a `kind: 'content'` node whose parent is a session-bearer; its children are the Blocks Claude returned.
- **Branches container**: a new `kind: 'branches'` node materializes when the user first branches inside a subtree. It holds Branch siblings and lands as the immediate next sibling of the source node. It is fractal — branches inside a Branch's Prompt produce another Branches container at that depth. It defaults to collapsed.
- **No Thread Root**: replaced by "session-bearer Content Node" — any Content Node carrying `metadata.sdkSessionId`. A Branch is also a session-bearer (with fork metadata). One concept, two ways to create one.
- **One verb**: Cmd+Shift+B (inclusive fork). What was Retry-from-here becomes "select one node up and Cmd+Shift+B." What was New-thread-sibling becomes "select the session-bearer or root and Cmd+Shift+B." The selected source node determines the fork depth.
- **Branching is prompt-level**: Cmd+Shift+B operates on a Prompt selection only, not on Block selections. v1's block-level branching is dropped.
- **One conversation-starting verb**: Cmd+Shift+T is dropped. Cmd+Enter on a Content Node is the sole gesture; it makes the node a Prompt and (if not already) makes the parent a session-bearer.
- **State on Prompt**: `metadata.state: 'streaming' | 'done' | 'cancelled' | 'interrupted'` moves from Turn Node to Prompt. Crash recovery scans Prompts in `streaming` state. Absence of `state` = unsent draft.
- **Tree shape decoupled from SDK session graph**: every Prompt holds its own `sdkMessageUuid` (the assistant message it produced). Every session-bearer holds `sdkSessionId`. The SDK owns conversation history; cedarpad's tree is a viewer over the session graph. Rearranging tree nodes (outdent, drag) does not change the SDK session each Prompt resumes.

## Why

The v1 model conflated three separable concerns into shared structure: rendering position, SDK session continuity, and conversation alternative-management. v1's "Thread Root has multiple Threads as children" tried to express forks with tree topology — but the SDK already has session-fork primitives (`forkSession` + `resumeSessionAt`), and using those means the tree can be a free rendering layer instead of a load-bearing data structure.

Specific drivers:

- **Linear continuation was broken.** Each `query()` got only the latest prompt string; no history reached the SDK across turns. Fixed in PR #27 by wiring `resume: sessionId`, but that fix only made sense once the tree-as-viewer / session-as-history split was clear. The same split makes branch verbs trivial: each Branch is a forked session, no history-cloning in our DB.
- **Turn Node was a wrapper without a job.** It existed to group Blocks under one SDK turn — but Blocks know which Prompt they belong to (they're its children directly), and the Prompt is the unit of "one query → one response." The Turn Node added a layer the renderer had to skip.
- **Three branch verbs were one verb under a coordinate change.** Inclusive vs. exclusive fork is a shift in which message UUID to fork at — and "which message" is fully determined by which node the user selects. Splitting it across three keybindings asked the user to choose the verb when their selection already determines the answer.
- **Cmd+Shift+T was a bookkeeping step.** Every conversation needs a topic; making the user explicitly mark a node as "this is a topic" before they can prompt under it added friction without information. The send action carries the same intent.

## Trade-offs accepted

- **No data migration.** Existing `.cedarpad/db.sqlite` files use `kind: 'turn'` and the old branching shape. v1.1 burns them — the only existing user is the developer, the data is dev fixtures.
- **Block-level branching is gone.** v1 let users branch from a tool_use or tool_result block ("what if Claude had used a different tool here?"). v1.1 only allows branching at the Prompt level. Re-running a tool with different parameters means re-prompting from one node up.
- **Kind != metadata enforcement gap.** A Branch is a `kind: 'content'` node positioned inside a Branches container, not a separate kind. The DB schema cannot CHECK-constrain that only Branches sit inside a Branches container — UI is the gate. Same precedent as Thread Root in v1. Acceptable for a single-user tool; revisit if collaborative editing is added.
- **Eager forking creates orphan SDK sessions.** Cmd+Shift+B calls `forkSession` immediately, even before the user types a prompt. Branches the user creates and abandons leave forked sessions in the SDK store. Cleanup deferred; future Hide-Done semantics on Branches can collect them.
- **Rendering complexity moves up.** The renderer now has to: collapse single-Branch Branches containers visually, pair adjacent tool_use+tool_result blocks for collapse, default-collapse tool blocks, default-collapse Branches containers, distinguish Prompts from generic Content Nodes by ancestor walk. The data model is simpler at the cost of more render-side rules. Net win because data shape changes are migrations and code is just code.

## Rejected alternatives

- **Keep Turn Node, add a "Branches container" alongside.** Considered briefly. Adds the Branches concept without earning the simplification — Turn Node still wraps Blocks, branch verbs still triplicate, Thread Root still distinct. We'd carry v1's complexity and v1.1's complexity at once.
- **Promote first branch retroactively** (wrap the existing linear flow into a "main" Branch under a new Branches container when user first branches). Considered as the natural way to keep both old and new branches symmetric. Rejected because "branches occur on some child" — branching is rarely at the root; pre-wrapping the entire conversation is restructuring the user's tree to express something they didn't ask for. Branches container appears only at the depth of the source.
- **Branch as its own kind.** Considered to give Branches first-class schema enforcement. Rejected because a Branch behaves identically to a Content Node (editable text name, holds children, zoomable) — only its session metadata differs. Promoting to a kind for the sake of CHECK constraints is overengineering for a single-user tool. `kind: 'branches'` (the container) is worth a kind because it has different rules; the items inside are not.
- **Three branch verbs preserved.** Considered keeping Retry and New-Sibling as keybindings for ergonomic reasons. Rejected because the simplification is the point — one verb, one selection = one fork. Users learn one rule.
- **Cmd+Shift+T retained as a "make this a topic explicitly" gesture.** Considered for users who want to scaffold a topic before prompting. Rejected: Cmd+Enter on a root-level Content Node already creates the session-bearer + an empty Prompt child, which scaffolds the same structure with one gesture instead of two.
- **Pair tool_use+tool_result as a synthetic parent Block in the DB.** Considered for cleaner default-collapse. Rejected because the SDK emits a flat block stream — synthesizing a parent at write time risks edge cases (out-of-order arrival, partial pairs from interrupted turns). The renderer can group adjacent matching blocks for the collapse affordance without changing the data model.

## What v1.1 doesn't change

- libSQL per-repo workspace model (ADR-0005).
- `src/contract.ts` as single source of truth for IPC + JSON columns (CLAUDE.md §7).
- Worktree-safe defaults (CLAUDE.md §6).
- Read-only tool allowlist (`Read`, `Grep`, `Glob`) at the SDK boundary.
- Crash-recovery scan-on-launch pattern (just keys off Prompt instead of Turn Node now).
